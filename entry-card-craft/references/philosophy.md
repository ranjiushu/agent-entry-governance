# 设计理据：为什么这么定（按需加载）

这里收的是理由，不是规则。规则在 ../SKILL.md；这里回答「为什么」。执行治理任务时不必读；需要向人解释这套判据、或者打算修改判据本身时再读。

## 核心假设：为什么要多排一道页面

整套判据压着一个假设：**协作里人仍然占主导，而人会累、会挑、会绕开负担重的东西。** 入口文档的读者是人——Agent 是第一读者，但这份文档能不能活下来由人决定。人读得进去，才会读、才会改、才会把自己的判断放进来；读不进去，它就定格成一份没人维护的旧说明书，Agent 每次开工拿到的上下文跟着一起腐烂。所以真正的目标是降低人的阅读负担，让人更快进入项目、更快发现文档说错了——省下来的是人机之间反复澄清的时间。

打印这一步就是这么来的。人感觉不到 token 与字节，感觉到的是页数、空白、和被折断的表格：Markdown 里一行超长的表格在编辑器里只是一坨，排到页面上才看得出它散架了。要让这类毛病显形，就得按人真正会读的形态看一遍。页数还额外给了两样别处拿不到的东西：一个能横向比较的刻度（同一套写死的排版标准），以及「简历就该是一页纸」这个来自读者的压力。它压的是取舍，不是门槛：为保住因果与最短路径多占的页面是正当开销，本项目自己的成员文档就有 2–3 页的。所以它不是仪式，是把「通读一遍」从态度变成可执行的动作：几页、末页空不空、有没有半张白页。

边界同样要说清。这一步花 1–2 秒和一次浏览器渲染，换不来内容（可读换不来内容），也管不了机器侧的预算（那是守卫的活，token 只管有没有失控）。它保证的只有一件事：这份文档至少被按「人要读的样子」看过一遍——而看过的文档，才有人愿意接着改。

## 为什么判决权在人，不在数字

入口文档没有客观最优解。「多大最合适」争论不出结果，因为答案取决于读者构成、任务分布、上下文价位——全是变量。能复核的标准只有一个：好看、易看、愿意看。「愿意看」的界定是读得下去、不被形式劝退，不是要写得动人。

可读性不只是礼貌，它是**分发机制**。GUI 让个人电脑走出实验室，Python 让编程散到非科班的人手里——它们赢的不是性能，是「不看你简历也敢上手」。文档同理：写得像人能读的，才会被接手、被引用、被发现错误、被传下去；读不进去的只有作者自己看得懂，也就活不过作者离开。所以默认读者定为不熟悉这个项目的人，而不是作者本人。

反过来也要认：可读换不来内容。空壳再顺眼也走不出去。判准是把真东西讲得人能进，不是把页面弄漂亮。

前提是协作里人仍然主导——人读得进去，才愿意改、愿意用、愿意把自己的判断放进来，最终产出未必比「机器最优排版」差。机器能强制的只有体积代理，所以分工是：token 管有没有失控，页面管判决。

## 为什么是「简历」

入口文档和简历共享同一个结构：写给陌生人看、篇幅有硬约束、撒谎或过期的代价直接、存在的目的不是被欣赏而是开启下一步——面试，或者一次协作。所以判断一段话的去留时，这个比方可以直接用：简历不放生平流水账，放「从哪来、现在怎样」；简历不能撒谎，也不该过期。

但这个比方**只借结构，不借说服**。入口文档不做叙事层面的优化，不必打动谁，把故事讲清楚即可。它服务的是**人际协同**：像简历撮合求职者和招聘者坐下来谈一样，入口文档让接手的人（人，或作为第一读者的 Agent）知道该从哪儿开始对话、该问什么。职能决定调性：它是交接说明的口吻，不是宣传文案，也不是流水账；详略取舍本身也在服务协同。

## 与 README 分工的详述

判据（代价结构、三个测试）在 SKILL.md §〇，这里补「简」与「历」的完整含义和两条推论的理由。

简历两件事。**简**——简洁明朗，一眼看懂这是哪儿、要守什么。**历**——来历与现状，它从哪来、现在处于什么状况。历是精选的轨迹，不是逐日生平；交代这些是为了让人知道现在该怎么配合它，不是为了说服谁。README 回答三件事：这个项目到底在干什么、要到哪里去、以及一部分影响上手的具体技术细节。它比简历更像项目自己的声音——同一个项目的 README，换个负责人就会换调性与取舍，不必求统一。

推论一，同一事实只写一处：简历写「有这条规矩、违反的后果、去哪看」，标准全文放 README 或更下游。若两处内容几乎相同，通常是一方放错了——README 写了「每次必知」，或者简历抄了百科。

推论二，过期的代价不一样：简历过期会直接导致错误动作，README 过期只是让人误解。所以简历宁短勿滥，README 宁可写全。
